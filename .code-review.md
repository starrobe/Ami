## Critical

### 1. Terminal.tsx: `useEffect` with `[]` calls a `useCallback` with declared dependencies (React hooks violation)

**File:** `/home/adon/Ami/src/terminal/Terminal.tsx`, line 8-24
**File:** `/home/adon/Ami/src/terminal/useTerminal.ts`, line 250 (initTerminal deps) and line 632

The `useEffect` in `Terminal.tsx` has an empty dependency array but calls `initTerminal()`, which is a `useCallback` that declares `[executeCommand, writePrompt, setRichContent]` as its dependencies. This is a violation of the React hooks exhaustive-deps rule. It works in practice only because all three dependencies are themselves stable (created via `useCallback` with `[]` deps), but this is fragile -- if any of those callbacks ever gains a real dependency in the future, the terminal data handler would silently operate on a stale closure.

**Fix:** Either move `initTerminal` into the `useEffect` body directly, or add `initTerminal` to the `useEffect` dependency array (with awareness that this would cause the terminal to be destroyed and re-created on those changes).

### 2. Command registry re-created on every execution

**File:** `/home/adon/Ami/src/terminal/useTerminal.ts`, lines 211-227

`createRegistry()` is called inside `executeCommand`, creating a brand-new `Map` and re-registering all 11 commands on every single command execution. This is unnecessary allocation and object churn. The registry is deterministic -- it should be created once (e.g., in a `useRef`) and reused across executions. The only dynamic piece is the history command (which reads from a ref) and the cd command (which also reads from refs), so these can safely be registered once.

**Fix:** Create the registry once in a `useRef` inside `useTerminal`, register all commands once, and reuse it in `executeCommand`.

## Important

### 3. Parser silently discards `--` style long flags

**File:** `/home/adon/Ami/src/commands/parser.ts`, line 16

```typescript
if (token.startsWith('-') && token.length > 1 && !token.startsWith('--')) {
```

Any token starting with `--` (e.g., `--help`, `--color=auto`, `--ignore-case`) is silently dropped into the `args` array as a plain argument. No command currently handles long flags, but the parser is the single entry point for all parsing and should at minimum preserve them in a separate field (or add a `longFlags` array to `ParsedCommand`) rather than silently reclassifying them.

### 4. Quoted strings in parser do not support escape sequences

**File:** `/home/adon/Ami/src/commands/parser.ts`, lines 38-48

Input like `echo "hello \"world\""` will produce the token `hello \` (the backslash is not interpreted). Escaped quotes and other common escapes (`\n`, `\t`, `\\`) are not handled.

### 5. `cd -` with no prior directory returns home instead of an error

**File:** `/home/adon/Ami/src/commands/builtins/cd.ts`, lines 15-21

`prevCwdRef` is initialized to `/home/user`. If `cd -` is the very first command issued (before any `cd` has changed directory), it navigates to `/home/user` and reports `~`. Real shells would print something like `bash: cd: OLDPWD not set`. This is misleading -- the user thinks they navigated somewhere, but they were already in `/home/user`.

**Fix:** Track whether `cd` has been called before (a boolean ref) and show an error message on the first `cd -`.

### 6. Path double-slash in grep tag-search branch

**File:** `/home/adon/Ami/src/commands/builtins/grep.ts`, line 38

```typescript
const entryPath = dirPath + '/' + name;
```

When `dirPath` is `/` (root), this produces `//filename`. The standard grep branch (line 107) correctly handles this with:

```typescript
const entryPath = dirPath === '/' ? `/${name}` : `${dirPath}/${name}`;
```

The tag-search branch should use the same pattern.

### 10. `ProfileInfo` interface is exported but never imported externally

**File:** `/home/adon/Ami/src/config.ts`, line 3

`ProfileInfo` is exported but no other file imports it. It is only used internally to type the `profile` array. Either un-export it or remove the export keyword. TypeScript's `noUnusedLocals` doesn't catch exports.

### 11. Duplicate column-layout logic

**File:** `/home/adon/Ami/src/terminal/useTerminal.ts`, lines 42-73 (`formatMatchList`)
**File:** `/home/adon/Ami/src/commands/builtins/ls.ts`, lines 61-88

Both files contain nearly identical columnar layout algorithms (calculate `maxLen`, `colWidth`, `numCols`, `numRows`, then iterate to build rows). This should be extracted into a shared utility in `src/utils/`.

### 12. Command names hardcoded in two separate places

**File:** `/home/adon/Ami/src/terminal/useTerminal.ts`
- Line 213-228: command registration in `executeCommand`
- Line 521: tab-completion command list `['cat', 'cd', 'clear', 'echo', 'grep', 'help', 'history', 'ls', 'pwd', 'theme', 'whoami']`

Adding a new command requires updating both the explicit imports/registration block and the tab-completion string array. If they get out of sync, tab completion silently fails for the missing command. Consider deriving the tab-completion list from the registry itself (which already exposes `getNames()`).

### 13. Hardcoded file-argument command list in tab completion

**File:** `/home/adon/Ami/src/terminal/useTerminal.ts`, line 528


This list determines which commands get filesystem path tab-completion. If a new file-operating command is added, this list must be manually updated. Consider making this part of the command definition (e.g., each handler could expose a `completion: 'file' | 'none'` property).

### 16. Missing content-type `<meta>` for theme-color

**File:** `/home/adon/Ami/index.html`

The HTML has no `<meta name="theme-color">` or `<meta name="color-scheme">`. Since the app supports theming (even if only one theme today), the theme-color meta should be set dynamically to match the terminal background so the browser chrome can blend.

### 17. `code` block detection heuristic in MarkdownView

**File:** `/home/adon/Ami/src/output/MarkdownView.tsx`, lines 26-32

```typescript
code: ({ className, children }) => {
    const isInline = !className;
```

Using `!className` to distinguish inline code from fenced code blocks is a heuristic. `react-markdown` passes `className: undefined` for inline code and `className: "language-xxx"` for fenced code. This works today but is fragile against changes in the markdown library. A more reliable approach is checking `node.tagName` or the `inline` prop if available.

### 18. `echo` command does not handle flags

**File:** `/home/adon/Ami/src/commands/builtins/echo.ts`

The `echo` command ignores any flags (like `-n` to suppress the trailing newline). For a portfolio terminal this is minor, but it means the command output always includes `\r\n`.

## Architecture Suggestions

### 19. Monolithic `useTerminal.ts` (641 lines) should be decomposed

**File:** `/home/adon/Ami/src/terminal/useTerminal.ts`

This single file handles: terminal initialization, dynamic addon imports, input processing (backspace, arrow keys, Ctrl+U/W/C/L, Tab completion, Shift+Tab, history navigation, suggestion display, text insertion), prompt writing, theme application, command execution, state management, and resize handling.

**Suggested split:**
- `useTerminal.ts` -- terminal lifecycle (init, dispose, fit, resize)
- `inputHandler.ts` -- all `onData` key-handling logic
- `completion.ts` -- tab-completion state machine and match formatting
- `suggestions.ts` -- history-based inline suggestion logic
- `prompt.ts` -- prompt rendering

### 20. Command auto-discovery instead of manual import + registration

**File:** `/home/adon/Ami/src/terminal/useTerminal.ts`, lines 9-19 (imports) and lines 211-227 (registration)

Every new command requires: (a) create the file, (b) import it in `useTerminal.ts`, (c) call `registry.register(...)` in `executeCommand`, (d) update the tab-completion command list, (e) add a description to `descriptions.ts`, (f) optionally update the file-argument list. A barrel file pattern or `import.meta.glob`-based auto-discovery would eliminate several of these steps and prevent drift.

### 21. No test files anywhere

There are zero test files in the entire project. Key untested logic includes:
- `parseCommand` tokenization and flag parsing
- `resolvePath` / `getNode` / `normalizePath` filesystem operations
- Command handler outputs for edge cases (missing files, invalid paths, etc.)
- Tab-completion state machine (this is complex logic)

At minimum, pure utility functions (`parser.ts`, `filesystem.ts`) should have unit tests.

### 22. State synchronized manually via refs + useEffect

**File:** `/home/adon/Ami/src/terminal/useTerminal.ts`, lines 87-94

```typescript
const cwdRef = useRef(state.cwd);
const historyRef = useRef(state.history);
const themeRef = useRef(state.theme);

useEffect(() => { cwdRef.current = state.cwd; }, [state.cwd]);
useEffect(() => { historyRef.current = state.history; }, [state.history]);
useEffect(() => { themeRef.current = state.theme; }, [state.theme]);
```

This pattern (dual state+ref and syncing via useEffect) is needed because the terminal `onData` callback captures refs at registration time. It works but is verbose and error-prone -- forgetting to sync a new piece of state to its ref would cause stale reads. Consider wrapping this pattern in a custom `useSyncedRef` hook.

### 23. No error boundary in the React tree

**File:** `/home/adon/Ami/src/App.tsx`

If any React component throws during render (e.g., MarkdownView, WhoamiPanel), the entire app crashes to a blank white screen with no recovery. An error boundary around the terminal content would at minimum allow the terminal to keep functioning and show an error message.

### 24. Read-only filesystem

The virtual filesystem has no mutation primitives (`mkdir`, `touch`, `rm`, `mv`, `cp`, write/append). This is likely by design for a portfolio terminal, but it means content is statically defined at build time and cannot be modified at runtime. If interactivity is desired later, the FS layer would need significant redesign to support mutable state.
